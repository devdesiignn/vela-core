# Schema Design

## Approach

Four entities: `stores`, `receipts`, `line_items`, `extraction_reviews`. Field design is based on analysis of real sample receipts across multiple stores, split into three tiers:

- **Required** — present on every receipt. Strict, non-null columns.
- **Common, optional** — present on most receipts but not all, or not always under the same label. Nullable columns.
- **Rare / one-off** — present on only one or two stores, or inconsistent even within a single store. Stored in a structured `extras` JSONB field rather than as dedicated columns, so adding a new store never requires a migration.

Every table has an `id` column as its primary key, type UUID (a random, unique 128-bit identifier, e.g. `a1b2c3d4-...`) instead of a simple auto-incrementing number. Reasoning: this schema is a shared contract meant to be read and written by multiple independent services, possibly in different languages. A UUID can be generated by any service on its own, with no risk of collision. An auto-incrementing number requires one central authority (this database) to hand out "the next number" — that doesn't fit a system where several services might need to create records independently. See [DECISIONS.md](./DECISIONS.md) for the fuller comparison.

Every table also has a `created_at` column (type `timestamptz` — a timestamp that includes timezone information, so "when" is unambiguous regardless of where the reading/writing service is located), automatically set to the current time when the row is inserted, via Postgres's `now()` function. This is standard record-keeping — it lets you answer "when was this added" without any extra work from whatever inserts the row.

## Extractor Interface

The contract an extractor writes against:

**Successfully extracted data** goes into `stores` / `receipts` / `line_items`, matching `schemas/store.schema.json`, `schemas/receipt.schema.json`, and `schemas/line_item.schema.json`.

```json
{
  "id": "44d21dc0-ada2-4b24-9ad4-91800c4922a9",
  "store_id": "6105a8cf-f678-48da-8ce2-89cfe24fb61a",
  "source_image_id": "img_full_001",
  "transaction_ref": "INV-2026-0042",
  "date": "2026-01-15",
  "total": 4300.0,
  "content_hash": "hash_full_receipt_001"
}
```

**Anything an extractor is uncertain about** — a low-confidence field, a disagreement between two extraction attempts, a missed item — goes into `extraction_reviews`, matching `schemas/extraction_review.schema.json`.

```json
{
  "id": "6dbdc6dd-37ff-42f9-bb7b-661740759ac4",
  "receipt_id": "44d21dc0-ada2-4b24-9ad4-91800c4922a9",
  "field_name": "total",
  "extractor_source": "extractor-a",
  "extracted_value": "4300.00",
  "confidence_score": 0.612,
  "flagged_reason": "low_confidence",
  "status": "pending"
}
```

## `stores`

Core store identity.

| Column       | Type        | Nullable? | What it means                                                                         |
| ------------ | ----------- | --------- | ------------------------------------------------------------------------------------- |
| `id`         | uuid        | no        | Unique identifier for this store row. See note above.                                 |
| `name`       | text        | no        | The store's name, e.g. "Supreme Pharmacy." Every store has one, so it's required.     |
| `address`    | text        | no        | The store's physical address. Every receipt sample had one, so it's required.         |
| `phone`      | text        | yes       | Phone number, if the store lists one. Nullable — only some stores show this.          |
| `email`      | text        | yes       | Email address, if listed. Only 2 of 7 sample stores had this, hence nullable.         |
| `website`    | text        | yes       | Store website, if listed. Only 1 of 7 sample stores had this, hence nullable.         |
| `created_at` | timestamptz | no        | When this store row was created in the database (not when the physical store opened). |

**Why `name` + `address` have a unique constraint:** without it, nothing stops the same physical store being inserted twice as two separate rows with different `id`s. The pair is used rather than `name` alone, since two different branches of the same chain could share a name but sit at different addresses — that's meant to remain two valid, separate rows. This is an exact-string-match constraint, same limitation as `receipts.content_hash`: two addresses that mean the same place but are formatted slightly differently (e.g. "St" vs "Street") won't be caught as duplicates.

## `receipts`

One row per receipt.

| Column                  | Type          | Nullable? | What it means                                                                                                                                                          |
| ----------------------- | ------------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                    | uuid          | no        | Unique identifier for this receipt row.                                                                                                                                |
| `store_id`              | uuid          | no        | A reference (foreign key) pointing back to a row in `stores` — which store issued this receipt. Every receipt has to come from some store, so it's required.           |
| `source_image_id`       | text          | no        | A reference back to the original photo/scan this receipt was extracted from — kept so you can always trace a database row back to the raw input it came from.          |
| `transaction_ref`       | text          | no        | The store's own transaction/receipt number — whatever it's called on the actual paper ("Sale Number," "Invoice No," "Receipt #"). Every receipt has some form of this. |
| `transaction_ref_label` | text          | yes       | The exact label the store used for the above (e.g. "Invoice No" vs "Receipt #"). Kept separately so that distinction between stores isn't lost.                        |
| `register_ref`          | text          | yes       | Which till/register/cash point issued the receipt, if shown ("Till 4," "Cash Point 2"). Not every store prints this.                                                   |
| `date`                  | date          | no        | The date on the receipt (just the date, no time-of-day). Every receipt has one.                                                                                        |
| `time`                  | time          | yes       | The time of day on the receipt, if printed. Nullable defensively, even though every sample receipt had one — a store might not always print it.                        |
| `staff_name`            | text          | yes       | The staff member's name, however the store labels it ("Cashier," "Served By," "Issued by"). Nullable since not every store shows this.                                 |
| `customer_name`         | text          | yes       | The customer's name, if the receipt records one ("Customer," "Client," "Received From"). Present on only 3 of 7 sample stores.                                         |
| `payment_method`        | text          | yes       | How the customer paid (cash, card, etc.), if shown. One sample store never printed this at all.                                                                        |
| `subtotal`              | numeric(12,2) | yes       | The pre-tax/pre-discount total, if the receipt itemizes it separately from the final total.                                                                            |
| `discount`              | numeric(12,2) | yes       | Any discount applied, if shown. Present on only 2 of 7 sample stores.                                                                                                  |
| `vat`                   | numeric(12,2) | yes       | Value-added tax amount, if charged. Seen only at one store, and only on some of its registers — see note below.                                                        |
| `consumption_tax`       | numeric(12,2) | yes       | A different tax label some receipts use instead of/alongside VAT. Same rarity as `vat`.                                                                                |
| `total`                 | numeric(12,2) | no        | The final amount paid. The one number every single receipt has — the only truly universal monetary field.                                                              |
| `total_in_words`        | text          | yes       | The total spelled out in words (e.g. "Four Thousand Five Hundred Naira"), if the store prints that. Seen at only 2 of 7 sample stores.                                 |
| `content_hash`          | text          | no        | A computed fingerprint (hash) of key receipt fields (store + transaction ref + date + total), used to detect duplicates — see below.                                   |
| `extras`                | jsonb         | yes       | A flexible bucket for anything not common enough to deserve its own column — see "Why `extras`" below.                                                                 |
| `created_at`            | timestamptz   | no        | When this receipt row was inserted into the database.                                                                                                                  |

**Numeric types explained:** `numeric(12, 2)` means a number with up to 12 total digits, always exactly 2 of them after the decimal point — the right type for money, since it stores exact values (unlike floating-point numbers, which can introduce tiny rounding errors that are unacceptable for currency).

**Why `content_hash` has a unique index:** a unique index means Postgres will _reject_ any attempt to insert a second row with the same `content_hash` value — it physically cannot happen. This exists because, in the sample data, the same physical paper receipt was photographed twice (the "Momrota Pharmacy" case) and would otherwise have been saved as two separate receipts, double-counting that spend. The hash is computed from fields that together uniquely identify one real-world receipt, so a re-photographed duplicate produces the same hash and gets blocked at insert time.

**Why `vat`/`consumption_tax` live on `receipts`, not `stores`:** you might expect "does this store charge VAT" to be a property of the store itself. The sample data showed otherwise — the same store had some registers/tills that charged VAT and others (at the same store) that didn't. So it's a property of the individual receipt/transaction, not something that could be looked up once per store.

## `line_items`

One row per line/product on a receipt.

| Column        | Type          | Nullable? | What it means                                                                                                                                                                                                        |
| ------------- | ------------- | --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`          | uuid          | no        | Unique identifier for this line item row.                                                                                                                                                                            |
| `receipt_id`  | uuid          | no        | Foreign key back to the `receipts` row this line belongs to. Every line item has to belong to some receipt.                                                                                                          |
| `description` | text          | no        | The product/item name as printed, e.g. "Paracetamol 500mg."                                                                                                                                                          |
| `quantity`    | numeric(10,2) | no        | How many units were purchased. Allows decimals (e.g. `2.5` kg of something sold by weight), not just whole numbers.                                                                                                  |
| `unit_price`  | numeric(12,2) | no        | Price per single unit.                                                                                                                                                                                               |
| `line_total`  | numeric(12,2) | no        | `quantity × unit_price` as printed on the receipt (stored directly rather than always recomputed, since the printed value is the source of truth).                                                                   |
| `line_order`  | integer       | no        | The position this line appeared in on the original receipt (1st line, 2nd line, ...) — needed because database rows have no inherent order; without this column you couldn't reconstruct the original line sequence. |

**Why `receipt_id` cascades on delete:** the migration sets `ON DELETE CASCADE` on this foreign key, meaning if a `receipts` row is ever deleted, every `line_items` row pointing at it is automatically deleted too — a line item can't meaningfully exist without its parent receipt, so this avoids orphaned rows.

**Note:** line items were the one part of the schema that was completely consistent across every sample store — no per-store quirks were found here, unlike the receipt-level fields above.

## `extraction_reviews`

This is the most complex table, because it's solving a genuinely harder problem than the other three: recording when an automated extraction process (an AI/OCR pipeline reading a receipt image) wasn't fully confident about what it read, so a human (or another agent) can check and correct it.

**One row = one candidate value, from one extractor, for one flagged thing.** A receipt that extracted perfectly, with no uncertainty anywhere, has _zero_ rows in this table — rows only exist for things that need a second look.

| Column             | Type              | Nullable? | What it means                                                                                                                                                                                                                                                             |
| ------------------ | ----------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`               | uuid              | no        | Unique identifier for this review row.                                                                                                                                                                                                                                    |
| `receipt_id`       | uuid              | no        | Foreign key back to the `receipts` row this review concerns.                                                                                                                                                                                                              |
| `line_item_id`     | uuid              | yes       | Foreign key back to a `line_items` row, only if this review is about one specific line item. See "Locating what's flagged" below.                                                                                                                                         |
| `field_name`       | text              | no        | Which field is in question — either a real column name (`total`, `quantity`, ...) or one of two special sentinel values. See below.                                                                                                                                       |
| `extractor_source` | text              | no        | Which agent/model produced this candidate value (e.g. `"claude-vision-v2"`, `"tesseract-ocr"`) — required because multiple agents can run on the same receipt, and you need to know whose answer this is.                                                                 |
| `extracted_value`  | text              | yes       | What that agent actually extracted for this field. Stored as plain text regardless of the field's real type, since this table has to hold candidate values for many different kinds of fields.                                                                            |
| `confidence_score` | numeric(4,3)      | no        | How confident that agent was in its answer, stored as a number from 0 to 1 (e.g. `0.412`). Low confidence is typically why the row exists at all. Kept as a 0–1 decimal in the contract; format it as a percentage (e.g. `0.412` → "41.2%") only at the point of display. |
| `flagged_reason`   | enum (fixed list) | no        | Why this row was created — see "flagged_reason vs status" below.                                                                                                                                                                                                          |
| `extractor_notes`  | text              | yes       | The agent's own free-text explanation, if it has one (e.g. "digit smudged, could be 1 or 4").                                                                                                                                                                             |
| `status`           | enum (fixed list) | no        | Where this review currently stands — see below. Defaults to `pending` when the row is first created.                                                                                                                                                                      |
| `reviewed_value`   | text              | yes       | The corrected value, once a human (or agent) resolves this review. Empty until then.                                                                                                                                                                                      |
| `resolution_notes` | text              | yes       | A human's explanation of the resolution, especially useful when `status = rejected` (i.e. "why couldn't this be resolved").                                                                                                                                               |
| `reviewed_by`      | text              | yes       | Who resolved this row — a name, device ID, or account identity, depending on how the reviewing service identifies people/agents.                                                                                                                                          |
| `created_at`       | timestamptz       | no        | When this review row was created (i.e. when the extraction pipeline first flagged it).                                                                                                                                                                                    |
| `resolved_at`      | timestamptz       | yes       | When this review was last resolved. Empty while `status` is still `pending`.                                                                                                                                                                                              |

**What "enum" means:** an enum (short for "enumeration") is a column restricted to one of a small, fixed set of allowed text values — Postgres will reject any value outside that list. This schema defines two enums:

- `flagged_reason_type`: `low_confidence`, `conflicting_extractions`, `validation_failed`, `illegible`, `manual_flag`
- `review_status_type`: `pending`, `resolved`, `rejected`

Using an enum instead of plain free-text here guarantees every row's `flagged_reason`/`status` is one of a known, meaningful set of values — nothing else, no typos, no inconsistent capitalization.

### Locating what's flagged

`line_item_id` (nullable) and `field_name` together answer "what exactly is this review about." There are three cases:

1. **A single field is wrong (the common case).** `field_name` holds the actual column name (`"total"`, `"quantity"`, `"staff_name"`, etc.). `line_item_id` is set if that field belongs to a specific line item, or left empty if it's a receipt-level field (like `total` on the receipt itself). A line item with 3 wrong fields produces 3 separate rows — one per field — all sharing the same `line_item_id`.

2. **The row itself is wrong** — meaning the extraction merged two purchased items into one line, split one item into two, or invented a line item that isn't really there. `field_name = "line_item"` (a literal sentinel value, not a real column name), and `line_item_id` points at the specific offending row. `reviewed_value` then holds either a full corrected line, or the literal text `"delete"` if the line item shouldn't exist at all.

3. **An item was missed entirely.** `field_name = "missing_line_item"`, `line_item_id` is empty (there's no row to point at — nothing was created). `extracted_value` is also empty, since nothing was extracted. `reviewed_value` holds the full item that should be added.

### Multiple extractors, multiple agents

`extractor_source` records which agent/model produced a given row. If more than one agent runs on the same receipt:

- **They agree** — no review row is created at all. The value is simply saved once, since there's nothing to review.
- **They disagree** — one row is created per disagreeing agent, all sharing the same `receipt_id` + `line_item_id` + `field_name` (so they're clearly linked as "different opinions on the same question"), each with its own `extractor_source`/`extracted_value`/`confidence_score`, and `flagged_reason = "conflicting_extractions"`. A human resolves the disagreement by setting the same `reviewed_value` and `status = "resolved"` on every row in that group at once.

### `flagged_reason` vs `status` — two separate questions

These two enums answer completely different questions, and it's easy to conflate them:

- **`flagged_reason` answers: "why does this row exist?"** — `low_confidence`, `conflicting_extractions`, `validation_failed`, and `illegible` are all things the extraction pipeline detects automatically, on its own, with no human involved yet. `manual_flag` is the exception: it's for when a human notices something wrong that the pipeline was actually confident about and got wrong anyway (e.g. the pipeline extracted ₦4,500 very confidently, but you happen to know the real total was ₦4,050 — nothing automatic would ever catch that).

- **`status` answers: "what happened when someone tried to deal with it?"** — starts at `pending`, and moves to either `resolved` (fixed) or `rejected`. Importantly, `rejected` does **not** mean "permanently unfixable" — it means "couldn't resolve this right now." A rejected row can later move to `resolved` if the correct value becomes known (e.g. you check a bank statement, or simply remember). This is a manual update to the row, not something that happens automatically.

So a single row's full life might look like: created with `flagged_reason = "low_confidence"`, `status = "pending"` → someone looks at it but can't tell what's right yet, sets `status = "rejected"`, `resolution_notes = "can't read the smudged digit"` → weeks later, the physical receipt turns up again and it's readable, someone updates the same row to `status = "resolved"`, `reviewed_value = "4050.00"`.

## Why `extras` instead of more columns

Forcing every rare field (barcode presence, website, items-count line, promotional footer text, return-policy text, secondary reference numbers) into its own column means most receipts would carry a long wall of empty (`null`) values, and every new store risks needing a brand-new migration just to capture the one unusual field only that store happens to print. A structured JSONB field (`extras`) keeps the required/common columns clean, and lets whatever's doing the extraction write down any store-specific oddities as a flexible JSON object, without `vela-core`'s schema needing to know about every store's layout in advance.
