# Engineering Decisions

A running log of the non-obvious choices made building this repo, and why. Schema-specific reasoning lives in [SCHEMA.md](./SCHEMA.md); this covers everything else plus the schema decisions that needed real back-and-forth to land on.

## Database & hosting

**PostgreSQL 16, not 17.** 17 is current stable, but 16 is more battle-tested and nothing in this schema needs 17-specific features. Chosen for maturity over novelty.

**Local dev via Docker Compose; prod is not assumed to be Docker.** `docker-compose.yml` exists purely to give contributors a disposable local Postgres. Prod may end up being a hosted provider (Supabase/RDS/Neon) or a separately-managed server — either way, this repo only needs to know how to _connect_ to prod (via `.env.production`), not how to provision it. If Postgres is ever self-hosted via Docker for prod, that's a separate, non-committed setup on that server — reusing this compose file as-is, with real secrets hardcoded into a committed file, was never the plan.

## Migration tooling

**node-pg-migrate over Prisma.** Prisma's schema (`schema.prisma`) would become the de facto source of truth, and it's a proprietary DSL — not something a Go or Python consuming service could read directly. That conflicts with this repo's explicit scope boundary: "don't assume every consuming service is written in the same language." node-pg-migrate migrations are close to plain SQL, and the actual cross-language contract is the JSON Schema in `schemas/`, not the migration tool's format.

**UUID primary keys, not serial/bigserial.** This schema is a shared contract consumed by multiple independent services. UUIDs can be generated by any service without a central sequence; serial/bigserial require a single authority (this database) to hand out the next number, which doesn't fit a cross-service data contract as cleanly.

**One migration file per table**, not one file for all four. Keeps each table independently revertible — `migrate:dev:down` can undo one table's creation without necessarily touching the others (though in practice FK order means they still have to roll back in dependency order).

**`stores` gained a unique constraint on `(name, address)` in a follow-up migration**, not the original `create_stores` one. The original migration shipped with no protection against inserting the same physical store twice as separate rows — an oversight, caught after the fact rather than a deliberate initial choice. Fixed as an additive migration rather than editing the original, since the original had already been applied and other migrations were built on top of it by the time this was caught. `(name, address)` together, not `name` alone, so two differently-addressed branches of the same chain remain valid as separate rows.

## Environment configuration

**Plain `.env` for dev, not `.env.development`.** Originally used `.env.development`/`.env.production` for clarity of naming, but Docker Compose only auto-loads a file literally named `.env` for `${VAR}` substitution. Keeping a separate `.env.development` meant either hardcoding credentials into `docker-compose.yml` (duplicating `.env.development`) or maintaining a sync step to copy one into the other. Renaming the dev file to plain `.env` eliminates the duplication entirely — Compose and the `migrate:dev*`/`db:seed:dev` npm scripts now read the exact same file, with zero sync step. `.env.production` keeps its explicit name since it's never auto-loaded implicitly — every prod command names it explicitly (`dotenv -e .env.production`, `docker compose --env-file .env.production`).

**`dotenv-cli`, not Node's native `--env-file` flag.** Node ≥20.6 supports `--env-file` natively, avoiding a dependency. But baking that into committed npm scripts means anyone (or any CI machine) on an older Node version gets a cryptic "unknown option" failure. `dotenv-cli` is a pinned dependency in `package.json`, so `npm install` guarantees identical env-loading behavior everywhere, regardless of the runtime's Node version.

**Explicit `-e <file>` per script, not `NODE_ENV`-based auto-detection.** Every migration/seed script names its env file directly (`dotenv -e .env -- ...`, `dotenv -e .env.production -- ...`). No script infers which file to load from `NODE_ENV` or any other implicit signal — this keeps it unambiguous, from reading the script alone, exactly which environment a command touches.

## Schema: `extraction_reviews`

This table went through the most iteration. Two designs were considered:

**Rejected: two-table split (`extraction_reviews` + `extraction_review_verdicts`).** The idea was one table for "what's flagged" and a second table for "each reviewer/agent's verdict on it," to support multiple agents reviewing the same field. Reverted before implementation — a simpler single-table design (below) already handles multi-agent review without a second table, and the split added join complexity without a corresponding benefit.

**Adopted: single table, one row per candidate value per extractor.** Each row represents one extractor's (agent's) candidate value for one flagged thing. Multiple agents disagreeing on the same field just means multiple rows sharing the same `receipt_id` + `line_item_id` + `field_name` triplet — agreement produces no extra rows at all, since a value all agents agree on is simply saved once, no review needed.

**`line_item_id` + `field_name` together locate what's under review, including two sentinel `field_name` values** (`"line_item"` for a wrong row — merged, split, or invented; `"missing_line_item"` for an item missed entirely) alongside real column names (`"total"`, `"quantity"`, etc.). This lets one table represent three distinct kinds of problems (field-level, row-level, missing-row) without three separate tables.

**`flagged_reason` and `status` are separate, independent enums, not one combined field.** `flagged_reason` (`low_confidence`, `conflicting_extractions`, `validation_failed`, `illegible`, `manual_flag`) answers "why did this row get created." `status` (`pending`, `resolved`, `rejected`) answers "what happened when someone tried to resolve it." `manual_flag` specifically covers a human noticing a wrong value the automated pipeline missed entirely (high-confidence but simply incorrect) — distinct from the four reasons the pipeline detects on its own.

**`status = 'rejected'` is reversible, not terminal.** It means "couldn't be resolved right now," and can move to `resolved` later once the correct value becomes known (e.g. checked against an external record). The transition isn't automatic — it's a manual update to the row, same as any other resolution.

**Table name stayed `extraction_reviews`, not `extraction_flags` or `extraction_issues`.** A rename was considered once the table's real shape became clearer (each row is closer to "a flagged problem + how it got resolved" than a simple "please review this"). Rejected for two reasons: `extraction_reviews` was already referenced elsewhere (this repo's own README, the wider platform's architecture docs), so renaming meant updating multiple places for a marginal wording improvement; and `extraction_issues` risked colliding with the unrelated concept of GitHub Issues, which this project's workflow also uses.

**Added a fourth `field_name` sentinel (`"receipt"`) plus a dedicated `flagged_reason` (`"extraction_failed"`) for total extraction failures.** Raised by a `vela-etl` handover: its Phase 2 orchestrator needed to represent "extraction produced nothing usable at all" (unreadable image, vendor API error) as an `extraction_reviews` row, and none of the original three `field_name` cases fit — they all presuppose some candidate value exists, even a wrong or missing-item one. `illegible` was considered as a reused reason but rejected: the existing seed example uses `illegible` for a single unreadable digit within an otherwise-successful extraction, not a whole-receipt failure — reusing it would blur "a value exists but is shaky" with "no value exists at all." Chose both a new sentinel (`field_name = "receipt"`, parallel to `"line_item"` but receipt-scoped) and a new enum value (`flagged_reason = "extraction_failed"`) rather than either alone, so the case is unambiguous whether code branches on `field_name` or on `flagged_reason`. `line_item_id` and `extracted_value` stay null, matching the existing `"missing_line_item"` pattern. Implemented as an additive migration (`addTypeValue` on `flagged_reason_type`) rather than editing the original enum's migration, since Postgres enum values can't be removed (`down` is a documented no-op).

## Data contract layout

**One JSON Schema file per table** (`schemas/store.schema.json`, `receipt.schema.json`, `line_item.schema.json`, `extraction_review.schema.json`), matching the four migrations 1:1, with `receipt.schema.json` referencing `line_item.schema.json` via `$ref` rather than embedding it. Chosen for symmetry and predictability — every table has exactly one matching schema file, easy to find, easy to keep in sync when a migration changes.

## Seed data

**Two files, not one: `seeds/fixed.js` (hand-written) + `seeds/random.js` (faker-generated).** Fixed data guarantees specific known cases always exist — a receipt with every optional field filled, one with only required fields, the per-register VAT case, and each of the three `extraction_reviews` cases (field-level, `"line_item"` sentinel, `"missing_line_item"` sentinel) plus a multi-extractor conflict. Random data (via `@faker-js/faker`) adds volume/variety on top, without needing to hand-write dozens of records. Neither alone was sufficient: fixed-only seed data doesn't exercise enough variety; random-only seed data can't guarantee a specific edge case exists to test against.

**`seeds/run.js` truncates all 4 tables before inserting, wrapped in one transaction.** Without this, re-running the seed script (e.g. every time `npm test` runs) fails on duplicate primary keys/unique constraints from the fixed dataset's hardcoded UUIDs and `content_hash` values. Truncating first makes the seed script idempotent — safe to run any number of times, always resulting in the same known-good state. The whole operation (truncate + both seed files) runs inside one `BEGIN`/`COMMIT` transaction, so a failure partway through rolls back cleanly instead of leaving the database half-seeded.

## Testing

**Two test files, not one combined file: `tests/schema.test.js` + `tests/seed.test.js`.** Schema tests verify what the _migrations_ produced (tables exist, the unique index on `content_hash` exists, both enums exist with the correct values) — these would still make sense even against an empty, unseeded database. Seed tests verify what the _seed script_ produced (row counts, FK integrity, enum values actually used) — these depend on seed data existing. Splitting keeps each file's assumptions explicit rather than blurring "does the schema look right" with "is the data internally consistent."

**`npm test` is fully self-sufficient via a `pretest` script** (`docker:up && migrate:dev && db:seed:dev`), rather than expecting the developer to have already run those commands manually. This mirrors the `predocker:up`-style npm hook pattern already used elsewhere in this repo — a single command should be enough to get from a cold start to a passing test suite, with no implicit setup steps to remember or document separately.
